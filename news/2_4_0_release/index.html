Diesel 2.4.0

Diesel 2.4.0 includes contributions from 76 people. Over a span of 14 months, more than 1337 commits were submitted.

This release introduces several large new features to Diesel and also expands the number of platforms on which you can run Diesel out of the box. Notable changes include:

  • Support for Database Views
  • Improved support for Enums
  • Support for batch update statements
  • Support for a distinct MariaDB backend
  • Extended support for SQLite functionality
  • Support for using Diesel in no-std Environments
  • Rust written migrations
  • #[derive(MultiConnection)] support in diesel-async

Besides these headline features, a significant amount of work was done to improve the robustness of the existing code. As part of this effort, we started fuzzing parts of Diesel and added support to run several tests using Miri and various sanitizers. This work helped uncover and fix various soundness and correctness issues, as well as bugs that could lead to panics. Most of the relevant fixes have already been backported to the various Diesel 2.3.x releases over the last few months.

Check out the full change log for a complete list of changes.

This release would not have been possible without the support of our contributors and sponsors. We would like to especially call out Prototype Fund for funding the development of the newly added support for views. We would also like to call out the Rust Foundation for recently sponsoring maintenance work on Diesel.

Nevertheless, the Diesel project is always looking for support. You can help by:

  • Contributing Code, Documentation, or Guides.
  • Answering questions in our discussion forum

  • Helping to triage issues in our issue tracker
  • Sponsoring the maintainers.

Database Views

Section titled “Database Views”

Diesel 2.4 introduces support for database views. It was already possible to use database views in previous versions of Diesel by manually writing table! definitions for your views and carefully only using methods that work with a particular view. Diesel 2.4 now introduces a view! macro that can be used to declare the existence of a database view. The syntax and usage of this macro closely mirror the existing table! macro, but the generated code prevents usage in any query other than SELECT statements.

Additionally, diesel-cli has been extended to support generating these view! definitions when you regenerate your schema.rs file via diesel print-schema or by running a new migration. Support for generating view! macro definitions can be enabled for existing projects by setting print_schema.include_views = true in your diesel.toml file. For new projects, this will be the default.

Finally, there is a new unstable print_schema.experimental_infer_nullable_for_views boolean configuration that enables inferring whether a view column might contain NULL values or not in more cases. By default, this configuration is disabled, causing Diesel to assume that most columns might contain NULL values, as reported by the underlying database system. This configuration enables an additional inference step to parse and verify the structure of relevant views to more accurately report possible null values. See this blog post from last year for more details. The underlying functionality is also available via a new diesel_infer_query crate for third parties. Since we still consider the results of this inference to be non-100% satisfying, this configuration is marked as experimental, meaning results might change in future Diesel versions. If you encounter a case that doesn’t work correctly, please report it in our issue tracker.

We would like to thank Prototype Fund again for funding the development of this feature.

Better Enum Support

Section titled “Better Enum Support”

Adding better support for mapping Rust enums to SQL values has been a long-standing request for Diesel. While such a mapping was possible for a long time, it either required significant custom code or the usage of a third-party crate. With Diesel 2.4, we finally introduce a new #[derive(Enum)] proc-macro to simplify the mapping of field-less Rust enums to SQL values.

This macro enables mapping a Rust enum to SQL side enum types (PostgreSQL, MySQL, MariaDB), integer fields (all backends), or text fields (all backends), depending on your database backend.

You can also use #[diesel(sql_types)] multiple times on the same enum to support mapping to several different types.

As part of this feature, we also added support via the Diesel CLI for automatically generating the corresponding Rust enum definitions for given SQL side enums, including the ability to generate migrations based on these definitions. Support for generating such definitions for existing projects can be enabled by setting print_schema.custom_enum_derives = true. For new projects, this will be the default.

Batch-Updates

Section titled “Batch-Updates”

diesel::update now supports updating multiple rows at once. SQL does not natively support this feature in a straightforward way for INSERT statements. Internally, we translate such an update request into a single UPDATE statement that assigns the correct values from a joined VALUES list based on the primary key. To enable this translation, we need to know both the values and the primary key simultaneously, which requires a struct that implements both Identifiable and AsChangeset.

Distinct MariaDB backend

Section titled “Distinct MariaDB backend”

MariaDB started as a fork of MySQL, so Diesel naturally supported MariaDB through the existing MySQL backend. However, over the last few years, MariaDB has added features and introduced changes to its database server and client that made supporting both systems with the same backend considerably harder. This created the need for a distinct backend and connection type for MariaDB in Diesel. With Diesel 2.4, we finally add a dedicated backend and connection type to Diesel. It still shares as much code as possible with the existing MySQL backend, but it allows Diesel to support MariaDB-specific features like RETURNING clauses more easily. Support for this new backend is exposed via the new mariadb feature for diesel and diesel-async.

Extended SQLite functionality

Section titled “Extended SQLite functionality”

Diesel 2.4 adds support for a lot SQLite functionality for managing database connection details. This includes support for the following features:

  • Auto extension callbacks for setting up a fixed set of functions, collections, or extensions for any SQLite connection created by a given process
  • A typed PRAGMA interface for reading and modifying database and connection level settings
  • Streaming BLOB support for reading large blob values in an incremental way
  • Support for setting limits and various other features to restrict what can be done with a specific connection
  • Support for various hooks to interact with events sent by SQLite internally
  • Attaching additional databases

Using Diesel in no-std Environment

Section titled “Using Diesel in no-std Environment”

Diesel 2.4 adds support for using the SQLite backend (via the new sqlite-no-std feature) with Rust targets that lack a standard library. This enables using Diesel with a SQLite database on embedded targets.

Such targets often have specific requirements for setting up the runtime. Please consult the documentation for the target you plan to use. Diesel and SQLite still require the usage of an allocator. Additionally, you need to supply a custom SQLite VFS to work with your environment. See the rsqlite_vfs for a Rust abstraction for building custom VFS, as well as a default in-memory VFS that works well with embedded targets.

See the complete example for more details on how to compile and use Diesel on an esp32-c6 with a bare-metal target.

Rust migrations

Section titled “Rust migrations”

Up until now, Diesel primarily expected users to write their database migrations using plain SQL, as that is often the most flexible solution for evolving your data requirements. Nevertheless, there was a long-running desire to also allow writing database migrations in Rust. With this release, we introduce RustMigrationSource, which easily allows registering migrations written in Rust. This type allows you to register migrations via callbacks, functions, typed migration builders, and custom types.

Diesel will then only execute migrations that have not yet been applied to the database, consistent with the existing migration framework. While we do not yet expose any query DSL constructs for the data definition part of SQL, this is planned for a future release.

As a secondary feature, we also introduced a CombinedMigrationSource type that allows you to mix migrations from different sources (e.g., plain SQL migrations and Rust-written migrations) in a straightforward way.

#[derive(MultiConnection)] support in diesel-async

Section titled “#[derive(MultiConnection)] support in diesel-async”

Diesel 2.1 introduced a #[derive(MultiConnection)] macro to Diesel, which allows an application to precisely describe which database backends it supports. Previously, this macro lacked support for diesel-async, making it difficult to write multi-backend applications using diesel-async. With this release, we introduce support for diesel-async within the #[derive(MultiConnection)] proc-macro, enabling its use with asynchronous connections.
